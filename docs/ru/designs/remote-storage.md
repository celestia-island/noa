# Проектирование серверных хранилищ (Remote Storage)

## Обзор

noa поддерживает подключаемые серверные хранилища (backends) для распространения
и резервного копирования объектов, адресованных по содержимому. Все хранилища
реализуют один и тот же трейт `ObjectStore`, поэтому снимки (snapshots), деревья
и блобы (blobs) можно отправлять в любое настроенное хранилище взаимозаменяемо.

## Поддерживаемые хранилища

| Хранилище | Идентификатор типа | Транспорт | Модель распространения |
|-----------|-------------------|-----------|------------------------|
| Redb (локальное) | — (всегда локальное) | Встроенная KV | Нет |
| IPFS (Kubo) | `ipfs` | HTTP API | Одноранговая (DHT, Bitswap) |
| S3 / MinIO | `s3` | API, совместимая с S3 | Централизованное хранилище объектов |

## Конфигурация

Удалённые хранилища сохраняются как массив `[[storage]]` в `.noa/config`:

```toml
[[storage]]
name = "ipfs-local"
type = "ipfs"
endpoint = "http://127.0.0.1:5001"
gateway = "https://ipfs.io"
auto_pin = false

[[storage]]
name = "s3-backup"
type = "s3"
endpoint = "https://s3.example.com"
bucket = "noa-objects"
access_key = "AKIA..."
secret_key = "..."
region = "us-east-1"
```

Каждая запись содержит `name` (для ссылок в CLI), дискриминатор `type` и поля,
специфичные для хранилища. Неизвестные поля для данного типа игнорируются.

## Паттерн фабрики

`create_remote_store(&StorageConfig) -> Box<dyn ObjectStore>` проверяет поле
`backend_type` и создаёт соответствующую реализацию:

```
type = "ipfs"  →  IpfsObjectStore  (HTTP-клиент reqwest → демон Kubo)
type = "s3"    →  MinioObjectStore (aws-sdk-s3 → S3-совместимая конечная точка)
```

## Мост CID для IPFS

noa идентифицирует объекты по SHA-256-хешам в шестнадцатеричной кодировке
(`BlobId`, `TreeId`). Для IPFS они преобразуются в CIDv1 (кодек raw) для вызовов
API:

```
байты CIDv1 = [0x01]           // версия 1
              [0x55]           // кодек raw
              [0x12]           // хеш-функция sha2-256
              [0x20]           // длина дайджеста 32 байта
              [32 байта хеша]

строка CIDv1 = "b" + base32_lowercase_nopad(байты CIDv1)
```

Это преобразование — чистая функция; одинаковое содержимое всегда отображается в
один и тот же CID. Для сопоставления не требуется обращения к демону.

## Выбор библиотеки: reqwest вместо ipfs-api-backend-hyper

Хранилище IPFS использует `reqwest` напрямую против HTTP API Kubo, а не крейт
`ipfs-api-backend-hyper`. Обоснование:

- `aws-sdk-s3` (уже является зависимостью) использует hyper внутри; добавление
  `ipfs-api-backend-hyper` рискует конфликтами версий hyper
- API Kubo достаточно прост для тонких REST-вызовов
- `reqwest` с `rustls-tls` избегает системной зависимости OpenSSL

## Стратегия отправки (push)

При отправке снимков noa рекурсивно обходит дерево:

1. Для каждого блоба в дереве: проверить, существует ли он удалённо → если нет,
   отправить
2. Для каждого поддерева: рекурсия
3. Отправить корневое дерево
4. Для IPFS с `--pin`: закрепить корневой CID, чтобы предотвратить сборку мусора

Это гарантирует, что полный граф снимка передаётся. Локальный `RedbObjectStore`
всегда является источником истины; удалённые хранилища — это цели
распространения/резервного копирования.

## Обработка ошибок

Ошибки, специфичные для хранилища, отображаются на варианты `NoaError`:

- `IpfsDaemonUnreachable { endpoint }` — соединение отклонено, тайм-аут
- `IpfsError { message }` — ответ об ошибке API
- `InvalidCid { cid }` — сбой преобразования SHA-256 → CID
- `ObjectNotFound { id }` — блок не найден в сети/хранилище

## Проектные решения

### Почему плоская структура конфигурации вместо размеченных перечислений?

TOML не имеет встроенной поддержки перечислений. Плоская структура с
дискриминатором `type` плюс необязательные поля, специфичные для хранилища, —
наиболее TOML-дружественный подход, и он соответствует существующему паттерну
`RemoteConfig` (`name` + `url` + `protocol`).

### Почему не объединить с `[[remotes]]`?

Git-ремоуты (`RemoteConfig`) и хранилище объектов (`StorageConfig`) служат разным
целям:
- **Ремоуты** предназначены для push/pull по протоколу git (распространение
  исходного кода)
- **Хранилище** предназначено для распространения объектов, адресованных по
  содержимому (снимки, блобы)

Их разделение позволяет избежать путаницы и допускает независимую настройку.

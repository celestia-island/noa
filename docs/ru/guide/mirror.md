# Зеркалирование и обратный поток

Система зеркал загружает в noa из внешних хостов (GitHub и т.п.) ветку master репозитория, все
теги и активные PR-головки; затем канал обратного потока отправляет состояние noa обратно в
origin — складывается переходная форма «noa как источник истины + зеркало GitHub», а farm/CNB
продолжают забирать изменения из GitHub, как и раньше.

## Задачи зеркалирования (MirrorJob)

```json
{
  "name": "noa",
  "remote_url": "https://github.com/celestia-island/noa.git",
  "github_slug": "celestia-island/noa",
  "branches": ["master"],
  "tags": true,
  "pr_heads": true,
  "backflow": true,
  "canary_push": true,
  "enabled": true
}
```

| Поле | Описание |
|---|---|
| `name` | `^[a-z0-9][a-z0-9-]{0,63}$`; также имя scratch-каталога, имя репозитория в каталоге и сегмент пути клонирования |
| `remote_url` | допускаются только `https://` / `file://`; встроенные учётные данные (`@`, `?`) отклоняются |
| `github_slug` | проверка формы `owner/repo`; используется обходом через Git Data API и обратным потоком |
| `branches` | хотя бы одна; отклоняются `tags`/`tags/*`, `pr/*` (конфликт пространств имён PR) и невалидные формы производных рабочих пространств |
| `tags` | зеркалирует все теги |
| `pr_heads` | зеркалирует активные PR-головки (`refs/pull/<N>/head` → `mirror/{job}/pr/<N>`) |
| `backflow` | каждую волну отправляет состояние scratch обратно в origin (подробнее ниже) |
| `canary_push` | отправляет одну пробную ссылку для проверки направления записи |
| `enabled` | когда выключено, планировщик пропускает задачу |

CRUD: `POST/GET /api/v1/mirror/jobs`, `DELETE /api/v1/mirror/jobs/{name}`,
`POST /api/v1/mirror/run` (ручной запуск, тело `{"job":"<name>"}`).

## Два канала

- **git-канал**: голый scratch-клон + `git fetch` — через него идут теги, PR-головки и push
  обратного потока.
- **API-канал**: когда git-транспорт отказывает (семейство сетевого джиттера), происходит
  автоматическая деградация к поблочному импорту через Git Data API; SHA каждого blob проверяется
  (точность не деградирует вместе с каналом).

Деградация выполняется на уровне волны: сбой `ensure_scratch` → волна идёт по API-каналу →
самолечение удаляет поломанный scratch, и следующая волна клонирует заново. Push обратного потока
работает только пока доступен git-канал (API не умеет отправлять ссылки).

## PR-головки

При `pr_heads: true` каждая волна дополнительно забирает `refs/pull/<N>/head` и импортирует её
как `mirror/{job}/pr/<N>` + рабочее пространство с тем же именем. Пространство имён PR и
пространство имён веток (ветки вида `pr/<x>`) взаимно исключаются и отклоняются при upsert.

## Обратный поток

```text
scratch local refs ──atomic push──▶ origin
  +refs/heads/*:refs/heads/*
  +refs/tags/*:refs/tags/*
  +refs/pull-heads/*:refs/noa/pr/*     (only when pull-heads exist in the scratch)
```

- **Учётные данные**: токен, разрешённый из `token_env` (по умолчанию `NOA_MIRROR_GH_TOKEN`),
  подставляется в одноразовый push-URL как `x-access-token:<token>`; токен никогда не попадает в
  конфиг scratch.
- **Семантика force**: после переключения noa — источник истины для записи, и ссылки origin
  сходятся к scratch. Асимметричное удаление (удаление на стороне noa не удаляет ссылку на стороне
  origin) — известное ограничение.
- **Семантика сбоев**: неудавшийся обратный поток помечает волну как FAILED — это канал, критичный
  для приёмки, и он должен оставаться заметным.
- **Мост пространств имён**: GitHub отклоняет push в `refs/pull/*`, поэтому PR-головки попадают в
  `refs/noa/pr/<N>`.

## Canary-проба

При `canary_push: true` каждая волна отправляет в origin пробную ссылку `noa-mirror-canary`
(коммит первой реплицированной ветки) — сначала через git-транспорт с деградацией до Git Data API
при сбое — непрерывно проверяя учётные данные и связность в направлении записи. Неудавшаяся проба
приводит к явному сбою волны.

## Проверка соответствия

Каждый импортированный коммит сверяется поэлементно: набор путей, тип записи и blob-OID
(`git_blob_oid` совпадает с git) должны совпасть точно; любое расхождение валит элемент и попадает
в детали ошибок волны. Обратный поток опирается на этот инвариант — объекты noa взаимно однозначно
отображаются на объекты git, поэтому push не требует слоя преобразования.

## Очистка устаревших ссылок (reconcile)

Наборы тегов и PR-головок из upstream образуют сверочный набор: ссылки, которых больше нет в
upstream, вычищаются из noa (пространства имён `mirror/{job}/tags/` и `mirror/{job}/pr/`). Push
тегов обратного потока также следует за upstream (удаление на стороне noa не удаляет сторону
origin — известная асимметрия).

## Планирование

При `NOA_MIRROR_ENABLED=1` планировщик раз в 900 секунд проходит раунд по всем включённым задачам;
`POST /mirror/run` запускает раунд вручную. Детали волны (канал, поэлементные результаты, статус
backflow/canary) доступны на `GET /api/v1/mirror/jobs` в полях `last_detail` / `last_lane`.

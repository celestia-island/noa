# Слияние и конфликты

Слияние в noa — двухслойная структура: «рекурсия по дереву + построчные листья». Каталоги
обходятся рекурсивно уровень за уровнем, а файловые конфликты сначала пытаются разрешиться
построчным трёхсторонним слиянием (diff3), при неудаче откатываясь к структурным конфликтам.

## Построчное трёхстороннее слияние (W2④)

При изменениях одного файла с обеих сторон сначала выполняется diff3-просмотр с общим предком в
качестве базы:

- **Области, тронутые только одной стороной**: берутся от этой стороны напрямую — непересекающиеся
  правки сливаются автоматически и больше не порождают конфликтов целого blob;
- **Пересекающиеся или смежные области** (как в git; нулевой зазор тоже считается конфликтом):
  генерируются блоки маркеров конфликта в стиле git (`<<<<<<< ours` / `=======` /
  `>>>>>>> theirs`), а структурный конфликт сохраняется для разрешения на стороне панели;
- **Полностью идентичные или нетронутые одной из сторон**: быстрый путь берёт их напрямую.

```rust
use libnoa::merge::line_merge::{merge_lines, LineMerge};

match merge_lines(base, ours, theirs) {
    LineMerge::Clean(merged) => { /* auto-resolved */ }
    LineMerge::Conflict { merged, ours, theirs, base } => { /* structured conflict */ }
}
```

## Точное переименование по содержимому (W2④ 刀二)

Когда одна сторона — «чистое переименование» (старый путь удалён, а то же содержимое blob дословно
появляется по новому пути), а другая сторона **изменяет старый путь**, правка автоматически
применяется по **новому пути** — классический сценарий rename+edit больше не порождает конфликта
«удаление против изменения».

Непокрытые случаи (консервативный откат к структурным конфликтам):

- переименование также изменило содержимое (payload-rename);
- обе стороны переименовали в разные цели;
- целевой путь тронут другой стороной (коллизия);
- переименование против удаления (переименование несёт содержимое базы и выживает по новому пути —
  семантика git с учётом переименований).

Эвристики сходства (определение переименований за пределами точных совпадений) — более поздний
срез.

## Семантика деградации

Когда построчное слияние недоступно (blob отсутствует/повреждён/бинарный/содержит одинокий CR),
файл откатывается к структурному конфликту целого blob — файлы **никогда** не отбрасываются
молча, и 500 никогда не возвращается. Форма фикстуры «пусто со всех трёх сторон» (хранилище
материализует отсутствующие id как пустые blob) деградирует так же.

## Поток слияния PR

`POST /api/v1/repos/{name}/prs/{number}/merge`:

1. трёхстороннее слияние снимков (base = база PR, ours = целевое рабочее пространство,
   theirs = PR-головка);
2. нет конфликта → дерево применяется автоматически + ссылки продвигаются;
3. конфликт → 409 + список конфликтов (путь + id blob ours/theirs/base); панель разрешает их через
   `ConflictResolution::{Ours, Theirs}`.

## Совместимость с git

Результаты слияния удовлетворяют объектной алгебре git: разрешённое дерево можно записать напрямую
обратно в scratch и отправить обратным потоком (push обратного потока + проверка соответствия,
ноль преобразований на всём пути).

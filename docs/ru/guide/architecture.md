# Обзор архитектуры

noa — распределённая система контроля версий, нативная для агентов. Это не «обёртка над git»:
базовая объектная модель с самого начала адресуется по содержимому (SHA-256), оставаясь побайтово
совместимой с объектной алгеброй git (один и тот же файл в noa и git даёт одинаковый blob-OID —
именно на этом держится проверка соответствия при зеркалировании).

## Трёхслойная модель

```
Workspace          — one isolated workspace per agent, invisible to each other
   │ head points to
Snapshot           — content-addressed commit (SHA-256), DAG structure (multiple parents = merge)
   │ tree_hash points to
ObjectStore        — blob / tree / symlink / gitlink, git object-algebra compatible
```

- **Рабочее пространство (workspace)** — базовый примитив изоляции noa: несколько агентов владеют
  своими рабочими пространствами и head внутри одного репозитория, не перезаписывая друг друга.
  Системные пространства имён вроде `mirror.<job>.<branch>` тоже существуют в форме рабочих
  пространств.
- **Снимок (snapshot)** — эквивалент коммита: `tree_hash` + `parents[]` + `author` + `timestamp` +
  `message`. Идентификаторы снимков выглядят как `noa_<sha256>` (адресация по содержимому;
  повторный импорт того же tree-хэша идемпотентен).
- **Ссылки (refs)** (RedbRefStore): `HEAD`, `mirror/{job}/{branch}`, `mirror/{job}/tags/{tag}`,
  `mirror/{job}/pr/{N}` и т.д. — всё это строки ссылок в redb, указывающие на идентификаторы
  снимков.

Движок хранения — однофайловое встроенное KV-хранилище (redb): развёртывание сводится к копированию
каталога, внешняя база данных не нужна.

## Компоненты сервера (noa-server)

| Компонент | Ответственность |
|---|---|
| REST API (`/api/v1/*`) | CRUD для репозиториев / PR / запусков / пользователей / задач зеркалирования |
| git-http (`/git/{repo}/*`) | смарт-HTTP: upload-pack (clone/fetch) + receive-pack (push, начиная с W2a2) |
| Движок зеркалирования | плановые волны: забор master / тегов / PR-головок из origin и импорт в noa; умеет выполнять обратный push |
| run-records | хранилище записей запусков CI (источник данных для DevOps-панели chest) |
| Посредник аутентификации | bearer-аутентификация на уровне маршрутов + применение ролей (REST) и проверка can_write (git push) |

Всё состояние сервера живёт в одной базе redb; сервер не имеет состояния вплоть до принципа
«каталог — это всё».

## Совместимость с объектами git

И импорт, и обратный поток исходят из неизменности объектной алгебры git:

- blob: необработанное содержимое — это тело git-blob (`git_blob_oid(content)` совпадает с git);
- tree: импорт сверяется поэлементно по path/kind/oid (проверка соответствия);
- commit: цепочку родителей поддерживают волны зеркалирования (адресация по содержимому
  `noa_<sha>` + ссылки на родителей).

Поэтому обратные push из noa → git не требуют слоя преобразования: git-объекты в scratch-клоне
взаимно однозначно соответствуют объектам noa.

## Роль scratch-каталога зеркала

`NOA_MIRROR_SCRATCH_DIR/{job}.git` — голый (bare) клон на каждую задачу зеркалирования с тройной
ролью:

1. **Кэш источника fetch** — волны делают fetch из origin; импортёр читает git-объекты отсюда;
2. **Обслуживающее тело для git-http** — `/git/{repo}` запускает upload-pack / receive-pack прямо
   поверх него;
3. **Источник push для обратного потока** — канал обратного потока атомарно отправляет свои
   локальные ссылки обратно в origin.

Push (receive-pack) обновляет локальные ссылки scratch; следующая волна импортирует их в систему
ссылок noa, а канал обратного потока отправляет их обратно в origin — все три пути делят один
scratch, и контур замыкается.

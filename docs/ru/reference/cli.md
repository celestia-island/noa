# Справочник CLI

`noa` — точка входа командной строки на стороне рабочего пространства (интерфейс порождается
через clap; актуальную сигнатуру см. в `noa --help`). Все команды выполняются внутри репозитория,
инициализированного через `noa init`.

## Обзор команд

| Команда | Назначение |
|---|---|
| `noa init` | инициализирует текущий каталог как репозиторий noa (создаёт каталог метаданных `.noa`) |
| `noa status` | текущее состояние рабочего пространства: head, незафиксированные изменения, список рабочих пространств |
| `noa log` | история снимков текущего рабочего пространства (усечённый рендеринг + обход цепочки родителей) |
| `noa snapshot` | операции со снимками (создание / просмотр) |
| `noa workspace` | управление рабочими пространствами: `workspace create <name>` (изоляция на каждого агента), переключение, список |
| `noa remote` | управление удалёнными репозиториями (add / set-url / list) |
| `noa push` / `noa pull` / `noa fetch` / `noa clone` | синхронизация с удалённым репозиторием (git-совместимая семантика) |
| `noa resolve <path>` | разрешает вложенный путь до записи дерева |
| `noa coauthor` | прикрепляет соавторов к коммитам (атрибуция сотрудничества агентов) |
| `noa hook` | управляет хуками репозитория (с маркером-сентинелом, безопасно перезаписывает существующие хуки) |
| `noa verify` | дописывает запись `verify.run/1` в журнал агентов текущего рабочего пространства (JSON через stdin или `--file`) — CLI-писатель реестра верификации |
| `noa sync` | операции синхронизации |
| `noa storage` | операции бэкенда хранилища |
| `noa pr` | жизненный цикл PR (независимо от forge): `pr create` / `pr list` / `pr diff` и т.д. |

## Рабочий процесс с изоляцией рабочих пространств

```bash
noa init
noa workspace create agent-a      # agent A's isolated workspace
# … edit inside the workspace …
noa snapshot -m "agent-a's changes"
noa log                           # sees only this workspace's parent chain
```

Несколько агентов каждый выполняют `workspace create`, будучи невидимыми для голов (head) и
содержимого друг друга — в этом принципиальное отличие noa от традиционных веточных рабочих
процессов: единица изоляции — рабочее пространство, а не ссылка (ref).

## Координация с сервером

push/pull/fetch/clone CLI взаимодействуют со смарт-протоколом `/git/*` сервера (та же
git-совместимая семантика). Для аутентифицированного удалённого репозитория учётные данные
подставляются из переменных окружения `NOA_GIT_USER` + `NOA_GIT_PASS` (подстановка и для
clone/push/pull; токен используется только для передачи и **никогда не записывается** в
`.git/noa/config`). Когда удалённый репозиторий указывает на noa-server:

```bash
noa remote add origin http://noa.example.com:3016/git/noa
noa push origin master
```

Push идёт через receive-pack и требует аутентифицированной идентичности (токен используется и как
пароль; роль должна иметь право записи). Обратите внимание: `noa push` публикует **текущий снимок
рабочего пространства** (на стороне клиента он сериализуется в git-коммит `[noa export]`) — после
правок сначала выполните `noa snapshot create` и лишь затем push; push без создания снимка
опубликует устаревший снимок.

## verify и реестр

`noa verify` — CLI-писатель реестра верификации: записи дописываются в журнал агентов текущего
рабочего пространства (JSONL, только добавление) со схемой `verify.run/1`. Записи могут нести
привязку `hardware=<hw-id>` (работает с аудитом реестра оборудования на стороне рабочего
пространства).

> Авторитетный реестр живёт на файловой стороне (`/mnt/work/verify-ledger/`); записи CLI —
> fail-open с двойной записью: писатели, не проверяющие цепочку, — проектное решение; проверку
> цепочки выполняют читатели.

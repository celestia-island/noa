# マージと競合

noa のマージは 2 層構造です: 再帰的な tree マージで、葉は行レベルです——ディレクトリは階層ごとにマージされ、ファイル単位の競合はまず行レベルの 3ウェイマージ（diff3）を試み、失敗した場合のみ構造化された競合へフォールバックします。

## 行レベル 3ウェイマージ（W2④）

同一ファイルへの両側変更に対して、共通祖先を基準に diff3 スイープを実行します:

- **片側だけが触れた領域**: その側を採用します——重ならない編集は自動的にマージされ、blob 全体の競合に潰されません
- **重なるまたは隣接する領域**（git と同じ扱い——ギャップゼロは競合と数えます）: git 形式の競合マーカーブロック（`<<<<<<< ours` / `=======` / `>>>>>>> theirs`）を生成し、パネルでの解決のために構造化された競合を保持します
- **同一または片側が未変更**: ショートカット経路が未変更の側を採用します

```rust
use libnoa::merge::line_merge::{merge_lines, LineMerge};

match merge_lines(base, ours, theirs) {
    LineMerge::Clean(merged) => { /* auto-resolved */ }
    LineMerge::Conflict { merged, ours, theirs, base } => { /* structured conflict */ }
}
```

## 同一内容リネーム（W2④ スライス 2）

片側が「純粋なリネーム」（旧パスを削除し、同じ blob 内容を新パスに再作成）で、もう片側が**旧パスを変更**している場合、その変更は**新パスに適用**されます——古典的な rename+edit のケースが、delete-vs-modify の競合を生むことはもうありません。

主張しないケース（保守的に構造化競合とします）:

- 変更された payload を伴うリネーム
- 両側が異なるターゲットへのリネーム
- ターゲットパスをもう片側が触れている場合（衝突）
- リネーム vs 削除（リネームはベースの内容を携えて新パスで生き残ります——git の rename 対応セマンティクス）

類似度ヒューリスティクス（非厳密なリネーム検出）は後のスライスです。

## 縮退のセマンティクス

行マージが使えない場合（欠落・破損・バイナリの blob、単独 CR の内容など）、ファイルは構造化された blob 全体の競合へフォールバックします——**決して**ファイルを黙って落とさず、500 も返しません。トリプルエンプティのフィクスチャ形状（欠落 id を空 blob として具現化するストア）も同じように縮退します。

## PR マージフロー

`POST /api/v1/repos/{name}/prs/{number}/merge`:

1. 3ウェイのスナップショットマージ（base = PR の base、ours = ターゲットのワークスペース、theirs = PR head）
2. 競合なし → ツリーが自動的に着地し、参照が進みます
3. 競合あり → 409 + 競合の一覧（パス + ours/theirs/base の blob id）。パネルは `ConflictResolution::{Ours, Theirs}` で解決します

## git 互換性

マージ結果は git のオブジェクト代数を満たします: 解決済みのツリーはスクラッチへ書き戻して還流できます（どこにも変換なしで push + 忠実度検証）。

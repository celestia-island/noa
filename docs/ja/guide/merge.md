# マージと競合

noa のマージは 2 層構造です——「tree レベルの再帰 + 行レベルの葉」: ディレクトリは階層ごとに再帰し、ファイル単位の競合はまず行レベルの 3ウェイマージ（diff3）を試み、失敗した場合のみ構造化された競合へフォールバックします。

## 行レベル 3ウェイマージ（W2④）

同一ファイルへの両側変更に対して、共通祖先をベースに diff3 の走査がまず実行されます:

- **片側だけが触れた領域**: その側から直接採用します——重ならない編集は自動的にマージされ、blob 全体の競合を生みません
- **重なるまたは隣接する領域**（git と同じ扱い。ギャップゼロも競合と数えます）: git 形式の競合マーカーブロック（`<<<<<<< ours` / `=======` / `>>>>>>> theirs`）を生成し、パネル側での解決のために構造化された競合を保持します
- **完全に同一または片側が未変更**: 高速経路がそのまま処理します

```rust
use libnoa::merge::line_merge::{merge_lines, LineMerge};

match merge_lines(base, ours, theirs) {
    LineMerge::Clean(merged) => { /* auto-resolved */ }
    LineMerge::Conflict { merged, ours, theirs, base } => { /* structured conflict */ }
}
```

## 同一内容リネーム（W2④ スライス 2）

片側が「純粋なリネーム」（旧パスが削除され、同じ blob 内容が新パスにそのまま再登場する）で、もう片側が**旧パスを変更**している場合、その変更は自動的に**新パス**に適用されます——古典的な rename+edit のシナリオが、「delete vs modify」の競合を生むことはもうありません。

主張しないケース（保守的に構造化競合へフォールバック）:

- リネームと同時に内容も変わった場合（payload を伴うリネーム）
- 両側が異なるターゲットへリネームした場合
- ターゲットパスをもう片側が触れていた場合（衝突）
- リネーム vs 削除（リネームはベースの内容を携えて新パスで生き残ります——git の rename 対応セマンティクス）

類似度ヒューリスティクス（完全一致を超えるリネーム検出）は後のスライスです。

## 縮退のセマンティクス

行レベルマージが使えない場合（blob の欠落・破損・バイナリ・単独 CR を含む場合など）、そのファイルは構造化された blob 全体の競合へフォールバックします——ファイルが黙って落ちることは**決して**なく、500 を返すこともありません。三辺がすべて空のフィクスチャ形状（ストレージが欠落 id を空 blob として具現化する場合）も同じように縮退します。

## PR マージフロー

`POST /api/v1/repos/{name}/prs/{number}/merge`:

1. 3ウェイのスナップショットマージ（base = PR の base、ours = ターゲットのワークスペース、theirs = PR head）
2. 競合なし → ツリーが自動的に着地し、参照が進みます
3. 競合あり → 409 + 競合の一覧（パス + ours/theirs/base の blob id）。パネルは `ConflictResolution::{Ours, Theirs}` に従って解決します

## git 互換性

マージ結果は git のオブジェクト代数を満たします: 解決済みのツリーはスクラッチへそのまま書き戻して還流できます（還流 push + 忠実度検証、全工程で変換ゼロ）。

# تصميم عزل مساحات العمل

## نظرة عامة

توفر مساحات العمل سياقات عمل معزولة للوكلاء والبشر. لكل مساحة عمل حالة مستقلة (لقطة الرأس، سجل الوكيل) مع مشاركة مخزن الكائنات الأساسي.

## هيكل مساحة العمل

```rust
pub struct Workspace {
    pub name: String,
    pub head: SnapshotId,     // اللقطة الحالية
    pub base: SnapshotId,     // نقطة التفرع من مساحة العمل الأم
    pub agent_id: Option<String>,  // الوكيل المرتبط
    pub created_at: u64,
    pub updated_at: u64,
}
```

## دورة حياة مساحة العمل

```mermaid
flowchart LR
    A["create"] --> B["switch"]
    B --> C["(الوكيل يكتب ملفات + لقطات)"]
    C --> D["merge"]
    D --> E["delete"]
```

### الإنشاء

```bash
noa workspace create feature-1
```

1. قراءة لقطة الرأس لمساحة العمل الحالية → تصبح `base`
2. مساحة العمل الجديدة: `head = base` (ترث الحالة الحالية)
3. إنشاء ملف سجل الوكيل: `agent-logs/feature-1.log`
4. التسجيل في WorkspaceStore

### التبديل

```bash
noa workspace switch feature-1
```

1. التحقق من وجود مساحة العمل
2. كتابة اسم مساحة العمل إلى `.noa/HEAD`
3. حفظ مساحة العمل السابقة إلى `.noa/ORIG_HEAD`

### الدمج

```bash
noa workspace merge feature-1
```

1. دمج ثلاثي: base → ours (الحالية) مقابل theirs (feature-1)
2. إنشاء لقطة دمج مع كليهما كآباء
3. تحديث رأس مساحة العمل الحالية

### الحذف

```bash
noa workspace delete feature-1
```

1. التحقق من أنها ليست مساحة العمل النشطة
2. إزالة مدخل مساحة العمل من المخزن
3. حذف ملف سجل الوكيل
4. الكائنات تبقى (مشتركة، معنونة بالمحتوى)

## ملف HEAD

يحتوي `.noa/HEAD` على اسم مساحة العمل النشطة:

```
feature-1
```

يحتوي `.noa/ORIG_HEAD` على مساحة العمل السابقة (للتراجع):

```
default
```

## مخزن مساحات العمل

تُخزن مساحات العمل في redb:

```
Table: workspaces
  Key:   "feature-1" (اسم مساحة العمل كـ &str)
  Value: msgpack(Workspace) كـ &[u8]
```

تحديثات الرأس تستخدم CAS (مقارنة-وتبديل):

```rust
async fn update_head(&self, name: &str, expected: &SnapshotId, new: &SnapshotId) -> Result<()>
```

هذا يمنع التحديثات المفقودة عندما تحاول عمليات متعددة تحديث نفس مساحة العمل بشكل متزامن.

## مقارنة مع فروع Git

| الجانب | مساحة عمل noa | فرع Git |
|--------|---------------|------------|
| التخزين | مدخل جدول redb | ملف مرجع (`.git/refs/heads/`) |
| العزل | ملف سجل وكيل خاص | فهرس مشترك + شجرة عمل |
| التبديل | كتابة ذرية لـ HEAD | استخراج شجرة العمل (I/O ملفات) |
| الإنشاء | O(1) — بيانات وصفية فقط | O(1) — خفيف الوزن |
| الحذف | إزالة من المخزن | حذف المرجع، تقليم اختياري |
| ربط الوكيل | حقل agent_id اختياري | لا مكافئ |
| تتبع القاعدة | حقل base صريح | ضمني (قاعدة الدمج) |

## مقارنة مع فروع SVN

| الجانب | مساحة عمل noa | فرع SVN |
|--------|---------------|------------|
| التخزين | مدخل KV | نسخ كامل للمجلد |
| الإنشاء | بيانات وصفية O(1) | نسخ ملفات O(n) |
| العزل | منطقي (كائنات مشتركة) | فيزيائي (مجلدات منفصلة) |
| تتبع الدمج | DAG الآباء | خصائص svn:mergeinfo |

## الأساس المنطقي للتصميم

### لماذا مساحات العمل بدلاً من الفروع؟

1. **هوية الوكيل**: تحمل مساحات العمل حقل `agent_id` للإسناد
2. **عزل سجل الوكيل**: لكل مساحة عمل ملف سجل مخصص
3. **لا شجرة عمل**: لا يحتفظ noa باستخراج — فقط لقطات
4. **قاعدة صريحة**: حقل `base` يتيح حساب قاعدة الدمج بسرعة

### لماذا لا يوجد استخراج لشجرة العمل؟

تتطلب فروع Git استخراج شجرة العمل (I/O ملفات لكل ملف مبدل). مساحات عمل noa تبدل مؤشرًا فقط — مرجع سجل الوكيل واللقطة. هذا O(1) بغض النظر عن حجم المستودع.

يتم تجسيد الملفات (الاستخراج) بشكل منفصل عندما يحتاج الوكيل إلى قراءة أو كتابة ملفات فعلية، باستخدام شجرة اللقطة كمصدر للحقيقة.

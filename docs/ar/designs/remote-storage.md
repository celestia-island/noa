# تصميم خوادم التخزين البعيدة

## نظرة عامة

يدعم noa خوادم تخزين بعيدة قابلة للإدراج لتوزيع ونسخ احتياطي للكائنات
المعنونة بالمحتوى. تطبق جميع الخوادم نفس السمة `ObjectStore`، لذا يمكن دفع
اللقطات والأشجار والقطع (blobs) إلى أي خادم مُعد بالتبادل.

## الخوادم المدعومة

| الخادم | معرّف النوع | النقل | نموذج التوزيع |
|--------|-------------|-------|---------------|
| Redb (محلي) | — (محلي دائمًا) | KV مدمج | لا شيء |
| IPFS (Kubo) | `ipfs` | واجهة HTTP API | نظير لنظير (DHT، Bitswap) |
| S3 / MinIO | `s3` | واجهة متوافقة مع S3 | مخزن كائنات مركزي |

## التهيئة

تُخزَّن الخوادم البعيدة كمصفوفة `[[storage]]` في `.noa/config`:

```toml
[[storage]]
name = "ipfs-local"
type = "ipfs"
endpoint = "http://127.0.0.1:5001"
gateway = "https://ipfs.io"
auto_pin = false

[[storage]]
name = "s3-backup"
type = "s3"
endpoint = "https://s3.example.com"
bucket = "noa-objects"
access_key = "AKIA..."
secret_key = "..."
region = "us-east-1"
```

لكل إدخال `name` (للمرجعية في CLI) ومميِّز `type` وحقول خاصة بالخادم.
تُتجاهل الحقول غير المعروفة لنوع معيّن.

## نمط المصنع

يفحص `create_remote_store(&StorageConfig) -> Box<dyn ObjectStore>` الحقل
`backend_type` ويبني التطبيق المناسب:

```
type = "ipfs"  →  IpfsObjectStore  (عميل HTTP عبر reqwest → خادم Kubo)
type = "s3"    →  MinioObjectStore (aws-sdk-s3 → نقطة نهاية متوافقة مع S3)
```

## جسر CID لـ IPFS

يُعرِّف noa الكائنات بتجزئات SHA-256 مشفرة بالنظام الست عشري (`BlobId`،
`TreeId`). بالنسبة لـ IPFS، تُحوَّل هذه إلى CIDv1 (ترميز raw) لاستدعاءات
واجهة برمجة التطبيقات:

```
بايتات CIDv1 = [0x01]           // الإصدار 1
               [0x55]           // ترميز raw
               [0x12]           // دالة التجزئة sha2-256
               [0x20]           // طول الملخص 32 بايتًا
               [32 بايت تجزئة]

سلسلة CIDv1 = "b" + base32_lowercase_nopad(بايتات CIDv1)
```

هذا التحويل دالة نقية — المحتوى نفسه يُعيَّن دائمًا إلى نفس CID. لا يلزم
الاتصال بالخادم لإجراء التعيين.

## اختيار المكتبة: reqwest بدلًا من ipfs-api-backend-hyper

يستخدم خادم IPFS مكتبة `reqwest` مباشرةً مع واجهة HTTP API الخاصة بـ Kubo
بدلًا من الحزمة `ipfs-api-backend-hyper`. المبررات:

- `aws-sdk-s3` (وهي بالفعل تبعية) تستخدم hyper داخليًا؛ إضافة
  `ipfs-api-backend-hyper` يُخاطر بتعارضات إصدارات hyper
- واجهة Kubo API بسيطة بما يكفي لاستدعاءات REST خفيفة
- `reqwest` مع `rustls-tls` يتجنب تبعية النظام OpenSSL

## استراتيجية الدفع (push)

عند دفع اللقطات، يتنقل noa في الشجرة بشكل تكراري:

1. لكل قطعة (blob) في الشجرة: التحقق مما إذا كانت موجودة عن بُعد → إن لم
   تكن، ادفعها
2. لكل شجرة فرعية: تكرار
3. دفع الشجرة الجذرية
4. بالنسبة لـ IPFS مع `--pin`: تثبيت CID الجذري لمنع التجميع الآلي للقمامة

يضمن هذا نقل الرسم البياني الكامل لللقطة. يكون `RedbObjectStore` المحلي
دائمًا مصدر الحقيقة؛ الخوادم البعيدة هي أهداف التوزيع/النسخ الاحتياطي.

## معالجة الأخطاء

تُعيَّن الأخطاء الخاصة بالخادم إلى متغيرات `NoaError`:

- `IpfsDaemonUnreachable { endpoint }` — رفض الاتصال، انتهاء المهلة
- `IpfsError { message }` — استجابة خطأ من واجهة برمجة التطبيقات
- `InvalidCid { cid }` — فشل تحويل SHA-256 → CID
- `ObjectNotFound { id }` — لم يتم العثور على الكتلة في الشبكة/المخزن

## قرارات التصميم

### لماذا بنية تهيئة مسطحة بدلًا من الأنواع المُوسومة؟

TOML لا يدعم الأنواع المُوسومة أصليًا. البنية المسطحة مع مميِّز `type`
بالإضافة إلى حقول اختيارية خاصة بالخادم هي أكثر نهج ملاءم لـ TOML، ويتطابق
مع نمط `RemoteConfig` الحالي (`name` + `url` + `protocol`).

### لماذا عدم الدمج مع `[[remotes]]`؟

ريموتات Git (`RemoteConfig`) وتخزين الكائنات (`StorageConfig`) يخدمان
أغراضًا مختلفة:
- **الريموتات** مخصصة لـ push/pull عبر بروتوكول git (توزيع الشيفرة
  المصدرية)
- **التخزين** مخصص لتوزيع الكائنات المعنونة بالمحتوى (اللقطات، القطع)

إبقاؤهما منفصلين يُجنّب الالتباس ويسمح بتهيئة مستقلة.

# مرجع CLI

`noa` هو نقطة دخول سطر الأوامر من جهة مساحة العمل (مشتق عبر clap؛ انظر `noa --help` للتوقيع الحي). جميع الأوامر تعمل داخل مستودع مهيأ بـ `noa init`.

## نظرة على الأوامر

| الأمر | الغرض |
|---|---|
| `noa init` | تهيئة المجلد الحالي كمستودع noa (ينشئ مجلد البيانات الوصفية `.noa`) |
| `noa status` | حالة مساحة العمل الحالية: الرأس، التغييرات غير المثبتة، قائمة مساحات العمل |
| `noa log` | تاريخ لقطات مساحة العمل الحالية (عرض مقتبوص + تجوال في سلسلة الأسلاف) |
| `noa snapshot` | عمليات اللقطات (إنشاء / فحص) |
| `noa workspace` | إدارة مساحات العمل: `workspace create <name>` (عزل لكل وكيل)، والتبديل، والسرد |
| `noa remote` | إدارة الأبعاد البعيدة (add / set-url / list) |
| `noa push` / `noa pull` / `noa fetch` / `noa clone` | المزامنة مع البعيد (دلالات متوافقة مع git) |
| `noa resolve <path>` | حل مسار متداخل إلى مدخل شجرة |
| `noa coauthor` | إرفاق مؤلفين مشاركين بالـ commits (إسناد التعاون بين الوكلاء) |
| `noa hook` | إدارة hooks المستودع (بعلامة حارسة، يكتب فوق الـ hooks الموجودة بأمان) |
| `noa verify` | إلحاق سجل `verify.run/1` بسجل الوكيل لمساحة العمل الحالية (JSON عبر stdin أو `--file`) — الكاتب من جهة CLI لسجل التحقق |
| `noa sync` | عمليات المزامنة |
| `noa storage` | عمليات الواجهة الخلفية للتخزين |
| `noa pr` | دورة حياة PR (مستقلة عن منصة الاستضافة): `pr create` / `pr list` / `pr diff` إلخ |

## سير العمل المعزول بمساحات العمل

```bash
noa init
noa workspace create agent-a      # agent A's isolated workspace
# … edit inside the workspace …
noa snapshot -m "agent-a's changes"
noa log                           # sees only this workspace's parent chain
```

عدة وكلاء يشغّل كل منهم `workspace create`، دون رؤية لرؤوس بعضهم أو محتواه — وهذا هو الفرق الجوهري بين noa وسير عمل الفروع التقليدي: وحدة العزل هي مساحة العمل، لا المرجع.

## التنسيق مع الخادم

يتكامل push/pull/fetch/clone في CLI مع البروتوكول الذكي `/git/*` الخاص بالخادم (دلالات git المتوافقة نفسها). مع بعدٍ بعيد يشير إلى noa-server:

```bash
noa remote add origin http://noa.example.com:3016/git/noa
noa push origin master
```

تمر الدفعات عبر receive-pack وتتطلب هوية مصادَقة (الرمز يعمل ككلمة مرور؛ ويجب أن يمتلك الدور صلاحية الكتابة).

## verify وسجل التحقق

`noa verify` هو الكاتب من جهة CLI لسجل التحقق: السجلات تُلحق بسجل الوكيل لمساحة العمل الحالية (JSONL، إلحاق فقط) وفق مخطط `verify.run/1`. ويمكن للسجلات أن تحمل ربطًا `hardware=<hw-id>` (بالتعاون مع تدقيق سجل الأجهزة من جهة مساحة العمل).

> السجل المرجعي يعيش في جهة الملفات (`/mnt/work/verify-ledger/`)؛ وكتابات CLI ثنائية الكتابة مع فشل متسامح (fail-open) — عدم تحقق الكتّاب المفتوحين للسلسلة حكم تصميمي؛ والتحقق من السلسلة تفعله القراءات.
